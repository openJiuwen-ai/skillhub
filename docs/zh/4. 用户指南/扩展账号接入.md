# 扩展账号接入（Keycloak / OIDC）

GitCode、GitHub、AgentOS 沿用原配置、OAuth 路由和用户资料请求。扩展渠道也使用同一组 `/api/v1/auth/oauth/{provider}/start|callback|session` 路由，由公共 OAuth 流程管理 state、pending、回跳和操作日志。
额外账号渠道通过配置和适配器目录启用，不需要增加渠道枚举或修改业务权限。
`MARKET_IDENTITY_EXTENSIONS_ENABLED` 是框架强制执行的总开关，默认 `false`；关闭或未设置时，所有扩展渠道均不可用。总开关开启但未设置 `MARKET_IDENTITY_EXTENSIONS_CONFIG` 时，也不会加载任何扩展渠道。GitCode、GitHub、AgentOS 不受这个总开关影响。

接入新的身份服务时，可直接从[新增其他适配器](#新增其他适配器)开始。该节以 `company-sso` 为例，覆盖复用 OIDC、实现独立适配器、部署和业务验收。

## Keycloak 配置

1. 在 Keycloak 中创建 OIDC 客户端 `skillhub`，开启客户端认证和 Standard Flow，使用 PKCE S256。
2. 注册精确回调地址，例如 `https://hub.example.com/api/v1/auth/oauth/enterprise/callback`。
3. 确保 userinfo 提供 `sub`、`preferred_username`；`name` 和 `picture` 可选。
4. 复制仓库 `config/identity-extensions.example.yaml` 到部署配置目录，填写 issuer、client ID 和回调地址。示例用 `enabled: true` 启用当前渠道；仍须在后端打开框架总开关。
5. 挂载适配器配置文件并通过部署环境注入客户端密钥，随后在后端配置中启用渠道。

```dotenv
MARKET_IDENTITY_EXTENSIONS_CONFIG=/app/config/identity-extensions.yaml
MARKET_IDENTITY_EXTENSIONS_ENABLED=true
MARKET_OAUTH_FRONTEND_ORIGIN=https://hub.example.com
MARKET_REVIEW_ADMIN_USERNAMES=reviewer01,reviewer02
```

配置路径是后端进程可读的路径。Docker Compose 的 backend 已读取 `.env`，但仍需把配置文件只读挂载进去：

```yaml
services:
  backend:
    volumes:
      - ../config/identity-extensions.yaml:/app/config/identity-extensions.yaml:ro
```

K8s / OpenShift 将上述变量写入后端 ConfigMap 的 `data`，用 ConfigMap 挂载 YAML，用 Secret 注入 `SKILLHUB_ENTERPRISE_SECRET`。模板里的 `MARKET_IDENTITY_EXTENSIONS_ENABLED` 默认为 `"false"`。配齐相关项后改为 `"true"`，再滚动更新后端。 [Kubernetes ConfigMap](../../../docker/k8s/marketplace-config.yaml) · [OpenShift ConfigMap](../../../docker/openshift/manifests/marketplace-configmap.yaml)
不要把密钥直接写在 YAML 中。`client_secret_env` 使用现有 SecurityUtils 读取，兼容现有密钥解密机制。
前端需要部署包含扩展入口的构建。使用已有适配器和通用登录按钮时，增减渠道只需更新配置和重启后端。
前端扩展代码集中在 `frontend/src/identity_extensions/`：`providers.ts` 处理共享渠道识别，
`registry.ts` 自动发现各账号体系的 UI 入口。授权和会话兑换统一使用现有 `frontend/src/api/auth.ts`，不再维护独立的扩展登录请求模块。
Keycloak 专属登录组件位于 `identity_extensions/keycloak/`，由该目录的 `index.ts` 导出。
站点配置返回的 `adapter` 字段选择对应目录，渠道 ID（例如 enterprise）不参与产品类型判断。
没有专属 UI 的账号体系使用公共登录按钮；旧版本后端未返回 adapter 时也使用公共按钮。
原有三个渠道保留原协议处理。其他渠道在公共 OAuth 路由中查询注册表并调用适配器，不增加产品名称分支。

本地开发可以在该适配器配置中设置 `allow_insecure_http: true`，并使用本地 HTTP 地址；生产默认要求 HTTPS。
浏览器和后端都需要访问配置的 issuer / Discovery 端点。不要把容器内部的 `localhost` 当成宿主机地址。

## 渠道与适配器

```yaml
providers:
  enterprise:
    enabled: true
    adapter: keycloak
    display_name: 企业账号登录
    settings:
      issuer: https://sso.example.com/realms/company
      client_id: skillhub
      client_secret_env: SKILLHUB_ENTERPRISE_SECRET
      redirect_uri: https://hub.example.com/api/v1/auth/oauth/enterprise/callback
      scopes: [openid, profile, email]
      token_endpoint_auth_method: client_secret_basic
      login_claim: preferred_username
      name_claim: name
      avatar_claim: picture
      algorithms: [RS256]
```

`enterprise` 是渠道 ID，用于 URL、`X-OAuth-Provider` 和 sessionStorage。
`keycloak` 是适配器包名，对应 `identity_extensions/keycloak/`，不是硬编码的渠道值。
同一适配器可以配置多个独立渠道。不同账号体系分别放在 `identity_extensions/<账号体系>/` 子目录中，
公共接口、注册表和扩展路由保留在根目录。已有配置中的 `adapter: oidc` 需要改为 `adapter: keycloak`。
渠道最终启用条件为：**框架总开关开启，并且渠道开关开启**。总开关关闭时，即使 YAML 写了 `enabled: true`，或者 `enabled_env` 指向的其他变量为 `true`，也不能加载或使用该渠道。

| 总开关 `MARKET_IDENTITY_EXTENSIONS_ENABLED` | 渠道开关 | 最终结果 |
|---|---|---|
| 未设置或 `false` | 任意值 | 所有扩展渠道关闭 |
| `true` | 关闭或未配置 | 当前渠道关闭 |
| `true` | 开启 | 当前渠道启用 |

渠道开关使用 YAML 布尔值 `enabled`，默认 `false`；也可用 `enabled_env` 指定独立环境变量。指定 `enabled_env` 后，它优先于该渠道的 `enabled`，变量值去除首尾空白、忽略大小写后为 `true` 时开启，未设置或其他值时关闭。已有 `enabled_env: MARKET_IDENTITY_EXTENSIONS_ENABLED` 配置继续兼容，但不能用其他渠道变量绕过框架总开关。

例如，需要单独控制企业渠道时，将该渠道的 `enabled: true` 替换为 `enabled_env: ENTERPRISE_LOGIN_ENABLED`，并同时配置 `MARKET_IDENTITY_EXTENSIONS_ENABLED=true` 和 `ENTERPRISE_LOGIN_ENABLED=true`。关闭其中任意一个开关，该渠道均不可用。

关闭总开关后，站点配置返回空的 `identity_extensions`，扩展渠道的 `/start`、`/callback`、`/session` 均返回 `404`；已有扩展 token 不能再通过 `/auth/me`、发布和审核等身份校验，沿用现有无效渠道错误约定。公开接口仍可匿名访问，原有资产不删除，身份服务本身的 token 和单点登录会话不会被撤销。后端不会读取适配器配置文件、发现或实例化插件，也不会使用扩展 token 查询内置厂商。

配置仍在进程启动时读取。修改总开关、渠道开关或 YAML 后须重启所有后端副本；ConfigMap 更新本身不会刷新进程环境和注册表缓存。无需重新构建前端，重新加载页面后登录入口随站点配置更新。
渠道 ID 只能包含小写字母、数字、下划线和连字符，以字母开头，最多 48 字符。
`gitcode`、`github`、`agentos` 是保留名，不允许扩展覆盖。
后端按渠道隔离初始化失败。某个渠道的配置不合法、Secret 缺失、插件导入失败、工厂抛异常或缺少必需的异步接口时，仅该渠道不注册，其他正常渠道仍可登录、发布和审核。错误渠道位于配置开头或结尾不影响结果。同一适配器的不同渠道分别构造实例，一个渠道缺少 Secret 不会影响另一个配置正确的渠道；模块自身无法导入时，依赖该模块的渠道均不可用，其他适配器可继续加载。关闭的渠道不导入插件、不调用工厂。

| 初始化错误范围 | 运行时处理 |
|---|---|
| 单个渠道的 ID、配置、适配器导入、工厂或接口错误 | 禁用该渠道，保留其他正常渠道 |
| 文件不存在、无法读取、YAML 语法或顶层结构错误 | 禁用全部扩展渠道 |
| YAML 重复键、非字符串键或其他歧义输入 | 严格拒绝整份配置，禁用全部扩展渠道 |

站点配置只返回正常渠道；失败渠道的登录、回调和会话兑换返回 `404`，其 token 不再用于业务鉴权，也不会转交给 GitCode。原 GitCode/GitHub/AgentOS 登录和鉴权不受影响，站点配置接口继续可用。

初始化日志仅记录安全元信息：渠道错误包含 `provider_id`、`entry_index`（从 0 开始）、`stage=provider_init` 和 `error_type`；非法渠道 ID 使用 `<invalid>`，通过序号定位。文件级错误使用 `stage=registry_init`。不记录异常正文、完整配置、token、Secret 或带敏感信息的堆栈，公开站点配置也不暴露初始化错误详情。

严格校验与运行时查询共用一次缓存的初始化结果。运行时返回其中正常的渠道，失败渠道不会在每次请求时重复导入或调用工厂；修正配置或补齐 Secret 后须重启全部后端副本。单次登录期间的上游故障仍由该渠道的请求处理，不会清空其他渠道的注册结果。

旧渠道用户资料查询直接进入原实现，不读取扩展注册表。总开关开启时，`registry.get_registry()` 会检查是否有渠道初始化失败，有失败则抛出包含安全渠道标识的 `ValueError`；它不会清空或重新构造运行时注册表。`IdentityRegistry(config)` 默认保持严格模式，直接遇到单渠道错误时抛出异常；框架通过容错模式构造缓存结果。`get_runtime_registry()` 返回可用渠道，仅遇到文件级或公共初始化错误时返回空注册表。两个公共入口均先检查总开关，再访问内部加载缓存；总开关关闭时返回空注册表，严格入口也不会读取和校验 YAML。

OIDC 通过 issuer 的 `/.well-known/openid-configuration` 获取端点，缓存元数据和 JWKS。

Keycloak 插件在加载配置时去掉 `settings.issuer` 的尾部斜杠，Discovery 请求、元数据校验和 ID Token 校验统一使用处理后的值。例如 `https://sso.example.com/realms/company/` 与不带尾斜杠的配置等效。Discovery 返回的 `issuer` 和 ID Token 的 `iss` 仍须与处理后的值完全一致，服务端返回值不做此处理。推荐直接填写 Discovery 响应中的 issuer。

这是 Keycloak 插件的配置约定，公共框架不会修改其他适配器的 issuer。其他 OIDC 服务若将尾斜杠作为 issuer 标识的一部分，需使用保留该标识的独立配置模型和适配器，不直接复用 `KeycloakConfig` 或下面转导出的 Keycloak 工厂。

适配器的 `settings` 可配置 `prompt: login`，让每次发起登录都要求重新认证，便于退出 Skillhub 后切换用户。省略该项时使用身份服务的单点登录行为。Skillhub 的退出操作清除应用登录态，Keycloak 浏览器会话可通过其账号页面或退出端点结束。
支持 `client_secret_basic` 和 `client_secret_post`，签名算法使用显式非对称算法白名单。
公共登录流程对扩展渠道执行 state 一次性消费和浏览器绑定 Cookie 校验；三个内置渠道沿用原 state 和会话行为。Keycloak 适配器实现 PKCE、nonce、签名/issuer/audience/有效期校验、
适用的 azp/at_hash 校验、JWKS 轮换重取，以及 ID Token 与 userinfo 的 sub 一致性检查。

## 登录与现有业务

```text
GET /api/v1/auth/oauth/enterprise/start
→ 第三方授权
→ GET /api/v1/auth/oauth/enterprise/callback
→ /login?oauth_session=...&oauth_provider=enterprise
→ POST /api/v1/auth/oauth/enterprise/session {"session":"..."}
→ GET /api/v1/auth/me
```

state 保留 600 秒；pending 保留 120 秒，两者一次性消费。
三个内置渠道的存储键和会话返回字段保持兼容。扩展渠道也使用公共 OAuth 存储键，按渠道 ID 隔离。升级前须将原 `/auth/extensions/...` 回调地址改为 `/auth/oauth/...`，同步修改身份服务客户端配置、适配器 YAML 并重启后端；旧的扩展路由不再注册，升级中未完成的扩展登录需要重新发起。
适配器返回的 `AuthorizationStart.callback_uri` 必须填写实际配置的完整回调地址。框架据其路径设置及删除浏览器绑定 Cookie，既支持根路径回调，也支持 `/hub/api/v1/auth/oauth/.../callback`；前端使用 `/hub` 且回调仍位于根路径时同样可用。
多进程/多实例部署仍须配置共享 Redis，沿用现有 OAuth 存储配置。
本地客户端可以在 start 传现有规则允许的 `redirect_to` 回环地址；整个授权过程仍使用浏览器完成。

后续请求：

```http
Authorization: Bearer <第三方access_token>
X-OAuth-Provider: enterprise
```

`sub → id → acting_user_id/publisher_id`，`preferred_username → login → 审核管理员名单匹配`。
现有 `/auth/me`、发布者归属、审核、默认禁止自审、组群 ACL 和通知逻辑继续复用。

## 操作日志与错误处理

扩展账号复用 Skillhub 的操作日志框架。公共 OAuth 路由对扩展渠道增加入口包装，在解析渠道和校验请求参数之前建立上下文，因此总开关关闭、未知或初始化失败的渠道、非法渠道 ID 和 `422` 参数错误也有对应的操作日志。GitCode、GitHub、AgentOS 请求直接走原处理器，保留原有协议、异常处理和操作日志行为。

| 操作 | `operation_type` | 操作者 |
|---|---|---|
| 发起第三方登录 | `oauth_start` | 匿名 |
| 接收认证回调 | `oauth_callback` | 校验成功前匿名，成功后为已验证用户 |
| 兑换一次性会话 | `oauth_session_exchange` | 成功后为该会话对应的已验证用户 |
| 查询当前账号 | `oauth_me` | 校验成功前匿名，成功后为已验证用户 |
| 发布和审核资产 | 沿用 `plugin_publish`、`skill_moderation` 等现有业务操作 | 沿用现有发布者和审核员身份 |

生产请求由现有中间件生成或校验 `request_id`，操作日志包含 `operation_id`、`operation_type`、`provider`、渠道资源标识、阶段和结果；身份验证成功后才写入真实 `actor_id`。非法渠道标识统一记为 `<invalid>`。每个 OAuth 请求只记录一条 `stage=complete` 的完成日志，已记录完成结果时公共异常处理器不再补录；必要的阶段诊断日志不计为第二条完成日志。回调失败可能通过 `302` 跳回登录页，应按操作日志的 `result`、`error_code` 和 `error_class` 判断，不能仅按 HTTP 状态判断登录成功。

公共框架统一调用适配器的三个接口。调用失败时可记录 `stage=adapter_call`、`phase`（方法名）和 `error_type`，这些诊断与当前操作共享上下文。适配器按约定抛出 `IdentityError` 或网络请求异常时，框架转换为安全的认证错误；`fetch_profile` 的这类失败按无效凭证处理。未预期的插件异常转换为安全的 `500` 错误，回调场景继续通过登录页错误跳转返回，不将原始异常交给堆栈日志。这些失败不会清空注册表或禁用其他正常渠道，总开关和初始化故障隔离规则保持不变。

扩展操作日志及公共插件异常日志不输出授权码、state、nonce、PKCE verifier、Cookie、客户端密钥、Token、完整回调参数、上游响应正文及原始插件异常正文或堆栈。适配器自行输出的日志也应遵守这一要求。新增插件继续实现原有三个接口，无须自行建立另一套登录操作日志。

操作日志通过现有日志配置输出到控制台及 `INTERFACE_LOG_DIR` 下的 `app.log`（目录默认 `logs`）。同一请求可通过 `request_id` 关联接口日志；登录发起、回调和会话兑换是不同 HTTP 请求，各自具有独立的操作 ID。本次接入未把凭证或 state 当作跨请求日志关联值。资产发布、审核继续使用现有数据库审计记录和审核历史；登录操作日志不会自动成为前端资产审核历史中的记录。初始化故障仍使用前文的安全诊断日志。
扩展账号不会自动获得系统管理员身份或批量导入权限。GitHub 标星仍要求 GitHub 授权。
现有 CLI 没有 provider 选项；扩展账号可使用上述 HTTP 请求头调用 API。

不增加用户表，不自动合并账号。ID 必须满足现有 64 字符字段，登录名/显示名最多 128 字符；
超长或与系统保留 ID 冲突时拒绝身份，而不是截断。
现有跨渠道 ID 和审核登录名碰撞风险仍由部署方管理。
更换身份服务/Realm 后须保持原 sub，或另行迁移资产、成员等归属；本功能不自动迁移。
登录态仍由前端 sessionStorage 保存第三方 access token；不新增 refresh token 自动续期或单点退出。

## 新增其他适配器

### 1. 选择接入方式

先核对身份服务提供的浏览器授权流程、后端凭证兑换接口和用户资料接口。当前公共回调接受带 `state` 的 **GET** 请求，登录结果使用 **Bearer access token**，后续 Skillhub 请求会继续用该 token 校验用户身份。对于只提供 SAML POST 等不兼容接口的系统，先通过身份网关提供兼容接口，或单独扩展公共登录协议。 [公共回调路由](../../../marketplace/plugins_market/routers/oauth_provider.py)

- **兼容当前 OIDC 实现**。身份服务提供 Discovery、授权码模式、PKCE `S256`、可验签的 ID Token 和 UserInfo，客户端认证支持 `client_secret_basic` 或 `client_secret_post`，且实际 issuer 不带尾斜杠。这类服务可以直接通过 YAML 指定 `adapter: keycloak`。现有适配器会发现端点、验证签名和声明，并核对 UserInfo 的 `sub`。 [OIDC 适配器](../../../marketplace/plugins_market/identity_extensions/keycloak/adapter.py) · [OIDC 配置字段](../../../marketplace/plugins_market/identity_extensions/keycloak/config.py)
- **认证或资料接口有专有要求**。在 `marketplace/plugins_market/identity_extensions/` 下新增与 `keycloak/` 平级的 Python 包，例如 `company_sso/`，在包内实现专有协议。

兼容 OIDC 的服务也可以拥有独立的适配器名和目录。在 `company_sso/__init__.py` 导出如下工厂后，即可在配置中使用 `adapter: company_sso`。

```python
from ..keycloak import create_adapter

__all__ = ["create_adapter"]
```

### 2. 为专有协议实现后端适配器

在 `company_sso/` 中用 `config.py` 定义并校验配置，用 `adapter.py` 实现协议逻辑，并从 `__init__.py` 导出工厂。配置字段按协议定义，可包含授权地址、凭证兑换地址、用户资料地址、客户端 ID、密钥环境变量名和回调地址。下面的例子假定配置模型使用 Pydantic。

```python
from .adapter import CompanySsoAdapter
from .config import CompanySsoConfig


def create_adapter(*, provider_id: str, settings: dict):
    return CompanySsoAdapter(provider_id, CompanySsoConfig.model_validate(settings))
```

公共注册表按 YAML 中的 `adapter` 自动发现对应的 Python 包，将渠道 ID 和该渠道的 `settings` 传给工厂。工厂做配置和密钥可用性校验。网络请求放在异步方法里，使用有界超时并及时关闭连接。新增依赖需要加入后端安装环境或镜像。 [注册表](../../../marketplace/plugins_market/identity_extensions/registry.py)

适配器实例实现以下三个 `async def` 方法。 [Python 接口和返回类型](../../../marketplace/plugins_market/identity_extensions/contracts.py#L13)

| 方法 | 实现要求 |
|---|---|
| `start_authorization(*, state)` | 将传入的 `state` 带入第三方授权地址，返回 `AuthorizationStart(url, transaction, callback_uri=配置的完整回调地址)`。回调地址须指向公共 `/api/v1/auth/oauth/{渠道ID}/callback`，可带对外部署前缀。`transaction` 保存回调需要的数据，例如 PKCE verifier 和 nonce，内容须能序列化为 JSON。 |
| `complete_authorization(*, callback_params, transaction)` | 按第三方协议校验回调及返回凭证，取得可信用户资料，返回 `LoginResult(access_token, user)`。`token_type` 默认是 `bearer`。 |
| `fetch_profile(access_token)` | 使用 token 查询并校验当前用户，返回与登录时使用相同映射的用户资料。token 无效或过期时返回 `None`。发布和审核也会调用此接口完成身份校验。 |

框架统一处理浏览器绑定、`state` 一次性消费、会话兑换和回跳白名单。适配器处理上游协议的验证，将授权或兑换失败转换为 `IdentityError`，错误信息只保留安全描述。

| 用户字段 | 映射要求和业务用途 |
|---|---|
| `id` | 必填，最多 64 字符。使用第三方稳定的用户标识，例如 OIDC 的 `sub`。Skillhub 用它记录资产发布者。新渠道接入前检查该 ID 与其他渠道及系统保留账号的冲突。 |
| `login` | 必填，最多 128 字符。使用经过验证的登录名，与 `MARKET_REVIEW_ADMIN_USERNAMES` 精确匹配。 |
| `name` | 必填，最多 128 字符。用作显示名，可在上游缺少姓名时使用 `login`。 |
| `avatar_url` | 可选，字符串或 `None`。 |

首次登录和后续 `fetch_profile` 调用应为同一用户返回一致的 `id` 和 `login`。发布者和审核员可以是第三方系统的普通账号，审核权限由 Skillhub 的审核名单授予。

### 3. 配置并部署新渠道

在部署使用的 `identity-extensions.yaml` 中，将下面的渠道追加到现有 `providers`。这是兼容 OIDC 且使用 `company_sso` 目录的示例。直接复用现有包时填 `adapter: keycloak`。使用专有协议时，按自己实现的 `CompanySsoConfig` 填写 `settings`。

```yaml
providers:
  company-sso:
    enabled: true
    adapter: company_sso
    display_name: 公司账号登录
    settings:
      issuer: https://login.example.com/oidc
      client_id: skillhub
      client_secret_env: SKILLHUB_COMPANY_SSO_SECRET
      redirect_uri: https://hub.example.com/api/v1/auth/oauth/company-sso/callback
      scopes: [openid, profile, email]
      token_endpoint_auth_method: client_secret_basic
      login_claim: preferred_username
      name_claim: name
      algorithms: [RS256]
```

- `company-sso` 是渠道 ID。回调路径和 `X-OAuth-Provider` 使用此值。`company_sso` 是适配器包名，须与目录名一致。`display_name` 是登录页显示的名称。
- 在第三方身份服务注册完整的 `redirect_uri`，并通过后端的密钥管理机制注入 `SKILLHUB_COMPANY_SSO_SECRET`。YAML 只保存环境变量名。编写专有适配器时可沿用 `SecurityUtils.get_decrypt_secret()` 读取密钥。 [密钥读取实现](../../../marketplace/common/security/security_utils.py)
- 将 YAML 挂载到后端可读位置，并将 `MARKET_IDENTITY_EXTENSIONS_CONFIG` 指向该路径，例如 `/app/config/identity-extensions.yaml`。`MARKET_OAUTH_FRONTEND_ORIGIN` 沿用 Skillhub 的现有前端地址。
- 始终将框架总开关 `MARKET_IDENTITY_EXTENSIONS_ENABLED` 设为 `true`，再通过 `enabled: true` 开启渠道。需要独立启停时，用 `enabled_env` 指定该渠道自己的环境变量，并同时打开总开关和渠道开关。Kubernetes 或 OpenShift 的 ConfigMap 中使用字符串 `"true"`。
- 部署包含新 Python 包的后端构建。仅更新配置和环境变量时，重启后端或滚动更新 Pod。部署期间可以用现有的 `/api/v1/site/config` 确认后端加载到的渠道。

上线前使用目标身份服务的两个账号完成以下验收步骤。

1. **检查总开关和渠道开关。** 保持渠道 `enabled: true` 或其独立开关为 `true`，将总开关设为 `false` 并重启全部后端副本，确认 `GET /api/v1/site/config` 的 `identity_extensions` 为空，扩展 `/start`、`/callback`、`/session` 返回 `404`，已有扩展 token 不能用于发布和审核。再开启总开关、关闭一个渠道并重启，确认该渠道不可用。两个开关均开启后，站点配置应返回 `id: company-sso`、`adapter: company_sso` 和对应的展示名。直接复用现有包时，返回的 `adapter` 为 `keycloak`。
2. **验证发布账号。** 普通用户用新渠道登录，确认 `/api/v1/auth/me` 返回预期的 `id` 和 `login`，再提交一个公开 Skill 并在「我的上传」查看版本状态。启用自动审查时，先等状态变为「审核中」。
3. **验证审核账号。** 将另一个账号的 `login` 加入 Skillhub 审核名单。用独立浏览器会话登录，确认 `/api/v1/auth/me` 返回 `is_market_moderation_admin: true`。从「待审核」打开该版本，审核通过后在「审核历史」确认记录。
4. **检查对外可见性和原有入口。** 在未登录会话中从公开市场找到已通过版本。用实例中已启用的 GitCode、GitHub 或 AgentOS 账号复查登录流程。
